# 工业 AI 辅助监控：可行性分析（定性）

> **目的**：评估「通过 MCP 协议把基于 LLM 的 AI 助手以**只读方式**接入工业监控，提供**建议**（而非控制）」这一方向的技术可行性。
>
> **性质**：本文档是**定性研究**，不含经济测算与真实工艺数据。所有设备参数与规则均为**通用示例**，仅用于说明概念，不代表任何真实工厂工况。

---

## 一、结论先行

**技术方向可行，但本仓库距离生产应用有本质差距。**

- ✅ 概念上可行：MCP 协议能把工业分析能力标准化地暴露给 LLM，只读接入在技术上有成熟方案（OPC UA 等）。
- ⚠️ 安全是前提：只读、人在回路、网络隔离必须从第一天就作为硬约束。
- ❌ 本仓库不是生产系统：它只包含几条启发式规则和仿真数据，用于说明「思路」，而非「可部署的方案」。

---

## 二、技术可行性

### 2.1 MCP 协议是否适合？

MCP（Model Context Protocol）把应用能力封装为 LLM 可发现的工具。工业领域已有同类实践（如面向 TIA Portal、CODESYS 的 MCP 桥），证明「把工程接口暴露给 AI」是可行的。

本仓库的做法：把**分析函数**（压力平衡、液位平衡等）封装为 MCP 工具。这是 MCP 最简单的用法——只暴露「读 + 算」，不暴露「写」。

### 2.2 数据接入是否可行？

- 仿真：完全可行（本仓库默认使用仿真适配器，无需任何硬件）。
- OPC UA：工业界广泛支持，只读接入成熟。但连接真实 DCS 需要权限、安全评估与网络隔离，本仓库只提供接口骨架，不提供生产配置。

### 2.3 分析能力是否可靠？

**不可靠。** 本仓库的分析是几条硬编码的启发式规则（如「压差为负 → 严重」），仅用于演示「领域知识可以被编码」这一概念。真实的异常检测需要：

- 经过验证的工艺模型与报警阈值；
- 历史数据训练的趋势 / 关联分析；
- 领域专家反复校准的规则。

这些都不在本仓库范围内。

---

## 三、安全边界（不可妥协）

| 原则 | 说明 |
| --- | --- |
| 只读 | AI 绝不向 DCS/PLC 写入任何值 |
| 人在回路 | 所有「建议」必须由操作员确认，绝不自动执行 |
| 物理隔离 | AI 层与控制网络之间用数据二极管 / 防火墙隔离 |
| 安全在硬件 | 安全联锁、安全继电器、安全 PLC 独立于 AI 之外 |

详细见 [security.md](security.md) 与 [safety-checklist.md](safety-checklist.md)。

## 四、当前实现 vs 愿景的差距

| 愿景 | 当前实现 | 差距 |
| --- | --- | --- |
| 有工程师经验的「数字人」 | 几条 if-else 规则 | 需要知识图谱、RAG、验证过的模型 |
| 链接笔记知识库 | 无知识库接入 | 需要检索增强、笔记结构化 |
| 实时帮助控制室 | 仿真数据 + 离线分析 | 需要真实数据接入、实时性设计 |
| 避免事故 | 仅演示异常检测思路 | 事故预防依赖安全仪表系统，不依赖 AI |

> 这些差距是**诚实标注**，不是缺陷清单——本仓库定位是「概念验证」，不承诺实现上述愿景。

## 五、通用示例数据声明

本文档及代码中出现的设备参数（如压力、温度、液位范围）与专家规则，均为**通用示例**，用于说明数据结构与规则形态，**不代表任何真实工厂的工艺参数**。若用于实际项目，必须替换为经工程验证的真实数据。

---

## 六、结论

「AI 通过 MCP 只读接入工业监控、提供建议」在概念上可行，且有工业界同类实践可参考。但：

1. 安全边界（只读、人在回路）是**不可妥协的前提**；
2. 本仓库只实现「思路的最小切片」，不是可部署方案；
3. 任何走向生产的尝试，都应由合格的工业自动化与安全专业人员主导。
